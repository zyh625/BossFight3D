# M8 调优与发布

## 这个里程碑解决什么问题

把"在编辑器里能玩"变成"别人下载就能玩、点开仓库就能看懂"：
一个可重复的 Windows 构建流程、一份 README，以及保证调试用的设置不会被带进发布版本。

## 做了什么

| 内容 | 位置 |
|---|---|
| 一键打包 | `WindowsBuilder`，菜单 `Tools/BossFight/5 Build Windows`，输出到 `Builds/Windows/BossFight3D.exe` |
| 调试数值与正式数值隔离 | `PlayerController`：体力消耗倍率只在编辑器里生效 |
| 退出游戏 | `QuitOnHoldEscape`：按住 Esc 1 秒退出 |
| 项目说明 | 根目录 `README.md`（玩法、操作、技术要点、架构图、文档索引） |

## 发布流程

1. `Tools/BossFight/Build All`：重建预制体和场景，保证它们和搭建脚本一致。
2. Test Runner → PlayMode → Run All：全部通过。
3. `Tools/BossFight/5 Build Windows`：打包。
4. 运行 `Builds/Windows/BossFight3D.exe` 完整打一局。
5. 把 `Builds/Windows` 整个目录压缩后上传到 GitHub Release。

这三步也可以不开编辑器，用命令行执行：

```
Unity.exe -batchmode -quit -projectPath <工程路径> -executeMethod BossFight.EditorTools.BuildMenu.BuildAll
Unity.exe -batchmode -projectPath <工程路径> -runTests -testPlatform PlayMode -testResults results.xml
Unity.exe -batchmode -quit -projectPath <工程路径> -executeMethod BossFight.EditorTools.WindowsBuilder.Build
```

## 关键设计取舍

### 1. 调试设置不能靠"发布前记得改回来"

测试阶段为了方便，把玩家的体力消耗调成了正式值的 0.4 倍。如果这个值只是配置资源里的一个数字，
发布时就得靠人记得改回 1——迟早会忘。现在的做法是：倍率仍然保存在配置里、在编辑器里随时可调，
但代码只在 `Application.isEditor` 为真时读取它，打出来的包固定使用 1。
代价：编辑器里的手感和发布版不完全一致。所以发布流程的第 4 步必须在真正的包里打一局，而不是只在编辑器里测。

### 2. 打包脚本和菜单是同一个方法

`WindowsBuilder.Build` 既挂在菜单上，也能被命令行的 `-executeMethod` 调用。场景列表、输出路径、
全屏模式都写在代码里，不依赖某台机器上 Build Settings 窗口里勾了什么。
构建失败时抛出异常，批处理模式会以非零退出码结束，脚本化流程才能发现失败。

### 3. 构建产物和第三方素材不进仓库

`Builds/` 在 `.gitignore` 里，可执行文件通过 GitHub Release 分发：仓库保持轻量，克隆很快。
Mixamo 的原始素材同样不进仓库（其条款不允许单独再分发），但包含在构建产物里是允许的。

## 面试时可能被问到的 3 个问题

### Q1：你是怎么保证发布出去的版本和你测试的是同一个东西？

答题要点：
- 场景和预制体由脚本生成，打包前先重新生成一遍，排除"手动改过但没记录"的差异。
- 打包配置（场景列表、目标平台、输出路径、全屏模式）在代码里，受版本控制。
- 自动化测试覆盖了从输入到扣血的主要链路，打包前必须全过。
- 调试专用的设置在代码层面被限制在编辑器内，不可能进入发布包。
- 仍然需要人工在真实的包里打一局：编辑器和独立运行在帧率、输入、着色器编译、字体等方面都可能不同。

### Q2：编辑器里能跑、打包后出问题，常见的原因有哪些？你遇到过吗？

答题要点：
- **着色器被裁剪**：只在代码里用 `Shader.Find` 引用的着色器不会被打进包。本项目的做法是所有材质都是资源，运行时代码不调用 `Shader.Find`。
- **只在编辑器存在的 API**：`UnityEditor` 命名空间的代码进不了包，所以搭建脚本放在只包含 Editor 平台的程序集里，个别辅助方法用 `#if UNITY_EDITOR` 包起来。
- **被裁剪的引擎模块**：项目的包清单是精简过的。例如截图模块不在清单里，调用 `ScreenCapture` 就会编译失败。
- **资源没被引用**：没有被场景或 `Resources` 引用的资源不会进包。
- **执行顺序和帧率**：编辑器里偶然成立的初始化顺序，在包里可能不同。本项目对有依赖的组件显式指定了执行顺序。
- 实际遇到的一个：自动化测试在批处理模式下帧率能到几千帧，模拟的按键偶尔不被识别，给测试限定帧率后稳定。

### Q3：如果要给这个项目加上持续集成，你会怎么做？

答题要点：
- 上面三条命令行就是流水线的三个阶段：生成 → 测试 → 打包。任何一步非零退出码就中止。
- 测试结果是 NUnit 格式的 XML，可以直接被 CI 平台解析并展示失败用例。
- Unity 需要许可证激活，CI 上通常用官方或社区的容器镜像，并把 `Library` 目录缓存起来避免每次重新导入。
- 构建产物作为流水线的附件保存；打标签时自动发布到 Release。
- 现状要说清楚：目前这些步骤是在本机用命令行跑的，没有接入真正的 CI 服务。
