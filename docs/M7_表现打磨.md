# M7 表现打磨：刀光、命中特效、残影、音效

## 这个系统解决什么问题

战斗规则在 M2~M6 已经完整，但"打中了"和"没打中"在画面和声音上区别太小。M7 给每个关键时刻加上反馈，
并且做到**不用任何外部素材**（贴图、模型、音频文件都没有），全部由代码生成——占位阶段就能看到效果，
之后换上正式模型和动画也不需要改。

## 核心类

| 类 | 做什么 | 由什么触发 |
|---|---|---|
| `WeaponTrail` | 刀光拖尾：把刀根—刀尖线段扫过的轨迹生成带状网格 | `Hitbox.Activated / Deactivated` |
| `ImpactVfx` | 火花、扩散光环、一次点光源闪光，按结算结果选择档位 | `DamageReceiver.Damaged` |
| `PulseRing` | 一圈向外扩散并淡出的光环（被 `ImpactVfx` 复用） | — |
| `AfterImageTrail` | 高速移动或瞬移时留下逐渐消失的残影 | 自己观察每帧位移 |
| `CombatSfx` | 挥砍、命中、格挡、识破、闪避的音效 | `Hitbox.Activated`、`DamageReceiver.Damaged` |
| `SfxSynth` | 用数学公式合成上面这些音效的波形 | 第一次用到时 |

所有组件都在 `Feedback` 程序集里，只订阅 `Combat` 层已有的事件。**玩法代码没有为 M7 改动一行**：
Boss 的招式状态里不存在"播放残影""播放音效"这样的调用。把这些组件全删掉，游戏照常运行。

各结算结果对应的反馈：

| 结果 | 画面 | 声音 |
|---|---|---|
| 命中 | 火花（数量随伤害增加）+ 受击闪白 + 短顿帧 | 打击声 |
| 被 Boss 格挡 | 少量冷色火花 + 小光环 | 高音金属声 |
| 识破 | 金色火花 + 两道光环（身前、脚下）+ 闪光 | 金属碰撞声 |
| 完美闪避 | 脚下青色光环（翻滚本身带残影） | 上扬的滑音 |
| 破防重击 | 最大档火花 + 两道大光环 + 闪光 + 特写 + 长顿帧 | 低沉的重击声 |

## 关键设计取舍

### 1. 刀光：自己生成网格，而不是用 TrailRenderer

TrailRenderer 只跟踪一个点，产生的是始终朝向相机的带子，适合拖尾光点；刀光需要的是
"刀根—刀尖这条线段在空间中扫过的曲面"，所以每帧记录两个端点，把相邻采样连成四边形。
- 采样之间用 Catmull-Rom 样条插值：0.1 秒的挥砍在 60 帧下只有 6 个采样，直接连线是明显的折线；
  Catmull-Rom 经过所有控制点，不会让刀光偏离实际轨迹。
- 透明度按采样的"年龄"平方衰减，判定结束后拖尾自然淡出。
- 顶点直接用世界坐标，网格放在场景根部——角色移动、转身不会拖着已经画出的刀光一起动。
- 代价：每帧重建网格。顶点数很小（几十到一两百），用预分配的 List 和 `Mesh.MarkDynamic`，没有 GC。

### 2. 一份加色材质打天下

刀光、火花、光环、残影共用 `FxAdditive.mat`：无光照、叠加混合、双面、不写深度，基础颜色是亮度 3 的 HDR 白。
实际颜色来自顶点色、粒子颜色或 MaterialPropertyBlock。
- 叠加混合下"越暗 = 越透明"，所以淡出只需要把颜色乘以一个系数，不用处理透明排序。
- 基础亮度大于 1，任何用它的东西都会超过 Bloom 阈值，自动带辉光。
- 同一材质的物体可以合批；用 MaterialPropertyBlock 改颜色不会产生材质实例。
- 代价：没有贴图，火花是被速度拉长的矩形，光环边缘是硬的。要更柔和需要贴图（见文末）。

### 3. 残影靠"观察位移"触发，而不是由招式通知

`AfterImageTrail` 每帧比较当前位置和上一帧位置：一帧内移动超过 2.5 米视为瞬移，沿路径补几个残影；
水平速度超过阈值则按固定间隔留残影。
- 好处：Boss 新增任何高速位移的招式，自动就有残影；玩家翻滚（7.5 m/s）有、奔跑（6.5 m/s）没有，只靠一个阈值区分。
- 残影复制的是当前网格：普通网格直接复用，蒙皮网格用 `BakeMesh` 烘出当前姿势。换成人形模型后不用改代码。
- 代价：阈值要和移动速度配合调；`BakeMesh` 有开销，所以用对象池并限制数量（12 个）。

### 4. 音效用程序合成

`SfxSynth` 直接计算每个采样的振幅，生成 `AudioClip`：
- 挥砍：白噪声过一个截止频率先升后降的低通滤波器。
- 打击：噪声爆发 + 110Hz 正弦，都做指数衰减。
- 金属声：四个频率不成整数倍的正弦叠加——非谐波泛音正是金属音色的特征。
- 随机数用固定种子，每次运行合成结果完全相同；每个音效只合成一次并缓存。
- 播放时随机微调音高（±8%），避免连续几刀听起来一模一样。
- 代价：音色比较"电子"，和这个项目的科技风格相符，但不如录制的素材有质感。之后可以整体替换成素材。

### 5. 特效物体全部预先创建、反复使用

粒子系统、光环、闪光灯、残影都在 `Awake` / `Start` 里创建一次，之后只是重新摆位置和启用。
战斗中不会 `Instantiate` / `Destroy`，没有因为特效产生的卡顿。

都在预制体的对应组件上（Player / ShadowSwordsman / TrainingDummy）：

| 想调什么 | 组件 | 字段 |

| 火花数量、光环亮度 | `ImpactVfx` | `baseSparkCount`、`sparksPerDamage`、`ringIntensity` |

## 面试时可能被问到的 3 个问题

### Q1：刀光拖尾是怎么做的？为什么不直接用 TrailRenderer？

答题要点：
- 每帧在 `LateUpdate`（动画更新之后）记录刀根和刀尖的世界坐标及时间戳，丢弃超过存活时间的采样。
- 相邻采样构成一个四边形（两个三角形），所有四边形连成带状网格；顶点色的 alpha 由采样年龄决定。
- TrailRenderer 跟踪单点、面片朝向相机，做不出"线段扫过的曲面"；并且它的宽度和朝向不受刀的姿态控制。
- 平滑：帧率有限导致采样稀疏，用 Catmull-Rom 插值（它经过控制点，不像贝塞尔会偏离轨迹）。
- 细节：顶点用世界坐标并把网格放在无变换的物体上；手动给一个大包围盒，避免每帧重算和被视锥剔除；
  `MarkDynamic` + 复用 List 避免 GC。

### Q2：你的特效和玩法代码是怎么解耦的？加一个新特效要改哪些地方？

答题要点：
- 玩法层只对外广播两类事件：`Hitbox` 的判定开启/结束，`DamageReceiver` 的结算结果（含结果类型、伤害、命中点、方向、攻击标记）。
- 表现组件各自订阅这些事件。玩法层不引用 `Feedback` 程序集，依赖方向是单向的。
- 加新特效 = 写一个新的订阅者组件并挂到预制体上，不需要改任何状态机或招式代码。
- 反例：如果在攻击状态里直接写 `PlaySlashEffect()`，每个招式都要记得调用，换特效要改招式，测试玩法还得带着特效资源。
- 实际验证：自动化测试在没有画面的批处理模式下运行，M7 加入后原有测试不需要任何修改。
- 残影更进一步：它连事件都不需要，只观察位移，所以对"谁在移动、为什么移动"完全无知。

### Q3：这些特效的性能开销在哪里？你做了什么控制？

答题要点：
- **不在战斗中创建/销毁对象**：粒子系统、光环、残影都是预创建的池，避免 `Instantiate` 的开销和 GC。
- **粒子**：一个角色只有一个粒子系统，用 `Emit` 按需发射，不自动播放；设置了最大粒子数。
- **Draw call**：所有特效共用一份材质，颜色通过顶点色或 MaterialPropertyBlock 传入，不产生材质实例。
- **过度绘制**是加色特效的主要成本（多层半透明叠加在同一像素上）：光环用很窄的环带而不是整个圆面，
  刀光存活时间只有 0.16 秒，残影限制数量和时长。
- **残影的 BakeMesh**（蒙皮网格）是 CPU 开销，所以按固定间隔而不是每帧生成。
- **音效**只合成一次并缓存；合成发生在第一次播放时，如果在意首次卡顿可以在加载阶段预热。
- 可以补充：现在的规模（两个角色）离瓶颈很远，这些做法主要是为了养成习惯和避免偶发卡顿，而不是因为测到了性能问题。

## 更新：场地改为明亮配色之后（M9）

场地从深色改成明亮配色后，加色混合的特效几乎看不见了——加色是"往背景上加亮度"，背景本来就亮时没有余量。
所以特效材质从加色混合改成了普通的透明混合（材质改名为 `FxGlow.mat`）：用特效的颜色盖住背景，在亮背景上同样清晰。
相应地，光环和残影的淡出方式从"把颜色乘暗"改成了"降低透明度"。上文"一份加色材质打天下"一节描述的是改动前的做法，
其中关于共用一份材质、用顶点色和 MaterialPropertyBlock 传颜色的部分仍然成立。
