# M1 角色基础：移动、相机、可替换的角色结构

## 这个系统解决什么问题

1. 让玩家角色能在场地里走、跑，第三人称相机跟随并可用鼠标环绕。
2. 从第一天起就把"逻辑"和"模型"分开，保证以后换成 Blender 模型不用改代码。
3. 让我（不能点编辑器）搭出来的场景和预制体可以一键重建。

## 模块与核心类

```
PlayerInputReader ──► PlayerController ──► PlayerMovement ──► CharacterMotor ──► CharacterController
    (读输入)            (每帧调度)        (相机相对方向+加减速)   (重力/贴地/转向)
                                                                    │ 实际速度
                                              LocomotionAnimDriver ◄┘──► CharacterVisual ──► Animator
                                              (速度 → Speed 参数)        (模型的唯一接口)

PlayerInputReader ──► OrbitCameraInput ──► CinemachineOrbitalFollow（相机绕角色的球面轨道）
```

| 程序集 | 类 | 职责（一句话） |
|---|---|---|
| Character | `CharacterMotor` | 位移的唯一出口：封装 CharacterController，处理重力、贴地、转向、瞬移 |
| Character | `CharacterVisual` | 逻辑访问模型的唯一接口：找 Animator、按枚举取骨骼、设置动画参数 |
| Character | `SocketBinder` | 启动时把武器/特效挂点挂到 Humanoid 骨骼上 |
| Character | `LocomotionAnimDriver` | 把实际速度写进 Animator 的 `Speed` 参数 |
| Character | `AnimParams` | Animator 参数名和哈希的集中定义 |
| Player | `PlayerInputReader` | 输入的唯一入口，把 Input Action 翻译成玩法能读的值 |
| Player | `PlayerMovement` | "自由移动"能力：输入 → 相机相对方向 → 带加减速的速度 |
| Player | `PlayerMovementConfig` | 移动调参数据（ScriptableObject） |
| Player | `PlayerController` | 每帧调度；M1 直接调移动，M2 换成状态机 |
| CameraRig | `OrbitCameraInput` | 鼠标位移 → Cinemachine 轨道相机的两个轴 |
| CameraRig | `CursorLocker` | 锁定/释放鼠标指针 |
| Editor | `BuildMenu` 及各 Builder | 一键生成层、材质、玩家预制体、动画控制器、场地场景 |

程序集依赖是单向的：`Character` ← `Player` ← `CameraRig`，`Editor` 引用所有。Character 不知道 Player 存在，所以 Boss 以后可以直接复用 `CharacterMotor` / `CharacterVisual` / `SocketBinder`。

## 关键设计取舍

### 1. CharacterController，而不是 Rigidbody

动作游戏要的是"我说移动多少就移动多少"：翻滚距离、突进距离、瞬移都要精确可控。Rigidbody 的移动结果由物理求解决定，会有惯性、被推开、摩擦等不可控因素，还要处理 FixedUpdate 和渲染帧不同步带来的抖动。CharacterController 是运动学的，每帧 `Move()` 立即生效，自带台阶和斜坡处理。
代价：没有物理交互（推箱子、被爆炸炸飞），重力要自己写——对 Boss 战来说这些都不需要，击退用代码位移即可。

### 2. 不用 Root Motion，位移全部由代码控制

动画只负责"看起来像"，位置由 `CharacterMotor` 决定。好处是换动画不会改变移动速度和招式位移，数值可以放在 ScriptableObject 里调；占位动画和最终动画可以随意替换。
代价：可能出现滑步（脚的移动和实际位移对不上）。缓解方法是让混合树的阈值等于动画本身的移动速度，并用实际速度（而不是输入）驱动混合。

### 3. `PlayerMovement` 不自己 Update，由上层调用 `Tick`

移动只是玩家的能力之一。M2 加入攻击、翻滚后，"现在能不能移动"由状态决定。如果 `PlayerMovement` 自己在 Update 里读输入并移动，每个新状态都得去关它；现在是状态主动调用，默认就是不动。同理 `CharacterMotor.Move(velocity, dt)` 的 `dt` 由调用方传入，之后做顿帧（只让被命中的角色停几帧）时只要改传入的 `dt`，不用碰全局 `Time.timeScale`。

### 4. 相机视角输入不乘 deltaTime

鼠标的 delta 本身就是"这一帧移动了多少像素"，已经包含了时间。再乘 `deltaTime` 会让灵敏度随帧率变化，并且在慢动作（`timeScale` 变小）时视角也变慢。所以 `OrbitCameraInput` 直接用"像素 × 每像素角度"，与帧率和时间缩放都无关。

### 5. 场景和预制体用 Editor 脚本生成

好处：可重复、可进版本控制审查（场景文件的 diff 没法读，生成脚本可以）、克隆仓库后一键恢复被 `.gitignore` 忽略的 Mixamo 相关资源。
代价：在生成的场景/预制体上手动做的修改，重新生成时会丢。约定是**数值调 ScriptableObject 和材质（脚本不会覆盖已存在的），结构改脚本**。

## 面试时可能被问到的 3 个问题

### Q1：你的角色移动为什么选 CharacterController 而不是 Rigidbody？

答题要点：
- 需求出发：动作游戏需要确定性的位移（翻滚、突进、瞬移的距离必须精确），不需要真实物理交互。
- CharacterController 是运动学的，`Move()` 当帧生效，自带 Step Offset、Slope Limit、碰撞滑动；不受力，不会被别的刚体推走。
- Rigidbody 在 FixedUpdate 更新，和渲染帧不同步，需要插值，否则相机跟随会抖；速度受摩擦、碰撞反弹影响，调手感更难。
- 代价要说清楚：重力、击退要自己实现；`isGrounded` 只在上一次 `Move` 有向下分量时才可靠，所以我在地面时保持一个小的向下速度（`groundedStickVelocity`）；瞬移要先禁用再启用 CharacterController，否则位置会被它覆盖。

### Q2：换一个模型，你的代码需要改哪些地方？为什么？

答题要点：
- 不用改。预制体结构是"逻辑根 + Visual 子物体"，脚本和碰撞都在根上，模型只是 Visual 下可整体替换的子物体。
- 动画用 Humanoid：动画数据存的是相对"标准人形骨骼"（Muscle 空间）的姿势，运行时通过每个模型自己的 Avatar 重定向到实际骨骼，所以同一份动画能驱动骨骼命名、比例都不同的模型。
- 代码不依赖骨骼名和层级路径，只通过 `CharacterVisual` 用 `Animator.GetBoneTransform(HumanBodyBones.X)` 取骨骼。
- 武器和特效挂在独立的 Socket 上，运行时由 `SocketBinder` 挂到骨骼下；Socket 的本地变换就是相对骨骼的偏移，换模型后只需微调这个偏移。
- 可以补充 Humanoid 的代价：重定向有少量 CPU 开销；不支持非人形的附加骨骼（披风、尾巴需要另外驱动）；手脚末端位置在比例差异大的模型上会有偏差，需要 IK 修正。

### Q3：相机相对移动是怎么算的？为什么角色的朝向不直接等于相机朝向？

答题要点：
- 取相机的 forward，去掉 y 分量后归一化，得到水平面上的"屏幕前方"；right 由 forward 旋转 90° 得到（`(f.z, 0, -f.x)`）；移动方向 = `forward * input.y + right * input.x`。
- 必须先去掉 y 再归一化：相机俯视时 forward 有很大的向下分量，不处理的话俯角越大移动越慢。
- 自由视角下角色朝向"移动方向"而不是相机方向，这样可以转动相机观察四周而角色不转身（类魂游戏的非锁定模式）；锁定模式（M3）下才改为始终面向目标、移动变成环绕平移。
- 转向用 `Quaternion.RotateTowards` 以固定角速度逼近，而不是直接赋值，避免反向输入时瞬间掉头。
- 速度用 `Vector3.MoveTowards` 做加减速，对速度向量整体插值，所以变向时会有自然的弧线而不是瞬间折线。
